# `bench/release_matrix/` — the release comparison harness

This is the harness behind [`docs/LcmsComparison.md`](../../docs/LcmsComparison.md).
It exists so the whole comparison can be produced in **one controlled
session on one machine**, rather than assembled from runs made months
apart — which is how the earlier figures ended up needing corrections.

Three engines, measured against the same bytes:

| engine | what it is |
|---|---|
| **jsColorEngine** | this library — pure-JS `int` kernels and the WASM SIMD tier |
| **lcms-wasm** | LittleCMS 2.16 compiled to wasm32, the engine a JS project would otherwise install |
| **lcms native C** | LittleCMS 2.18 compiled by gcc — the goalpost |

The native half lives in [`../lcms_c/bench_content_matrix.c`](../lcms_c/bench_content_matrix.c)
and is kept in lockstep with `run.js`: same six workflows, same five
content generators, same PRNG constants, same profiles, same photo bytes.

> **To reproduce the whole published comparison, use
> [`bench/reproduce.js`](../reproduce.js)** — one command, all seven
> phases, raw output plus a captured conditions block written to
> `bench/results/<timestamp>/`. The instructions below are for driving
> this harness directly when you are chasing a single figure.

## Running it

```bash
node bench/release_matrix/make_corpus.cjs
```

Decodes the five source photographs in [`images/`](./images/CREDITS.md)
and writes raw interleaved planes into `corpus/`. Both harnesses read
those planes, so both measure identical pixels. It also writes the CMYK
separation of each frame, because the CMYK-source workflows need real
CMYK input: random CMYK would misrepresent the content axis, since
separation changes adjacency.

**The source images are committed** (Unsplash licence — see
[`images/CREDITS.md`](./images/CREDITS.md)) so anyone cloning the repo
can reproduce the published figures; a benchmark whose input cannot be
obtained is not a benchmark. They add ~1.1 MB to the repository and
nothing to the npm package, since `bench/` is excluded from the tarball.
The decoded `corpus/` planes are gitignored: ~27 MB of derived data,
regenerated by the command above.

```bash
cd bench/release_matrix && npm install
node run.js --isolate --sizes 1048576       # content x engine, one process per cell
node run.js --isolate --sizes 16384,65536,1048576,10485760 --content noise
node run.js --pixelcache --sizes 262144     # pixel cache, accuracy path
node run.js --cell 2:photo:simd:1048576     # one number, for chasing an oddity
```

**Always use `--isolate` for anything you intend to publish.** Without
it the whole matrix runs in one process and the rows stop being
comparable — see rule 6.

```bash
# native side, in WSL/Linux
cd bench/lcms_c
bash flag_sweep.sh                          # pick CFLAGS first — see below
gcc -O2 -std=c99 -I lcms2-2.18/include -o /tmp/bm_O2 \
    bench_content_matrix.c lcms2-2.18/src/*.c -lm
taskset -c 0 /tmp/bm_O2 --sizes 1048576
```

## The six rules this harness enforces

**1. Give lcms its best build.** `flag_sweep.sh` builds lcms under seven
CFLAGS sets and measures each. On a Ryzen 7700X, `-march=native` is at or
near the bottom on every workflow, and no single set wins everything —
`-O2` takes the RGB-source workflows, `-O3` the CMYK-source ones. Quote
lcms's best build *per workflow* and say which it was. A comparison that
hands the other engine a worse compiler flag is worth nothing.

**2. Always run the cache axis.** lcms memoises the previous pixel
inside `cmsDoTransform`. Every content row is therefore measured twice,
with `flags = 0` and with `cmsFLAGS_NOCACHE`. Where the two agree, the
figure is the transform's real throughput; where they diverge, the gap is
the memo cache and nothing else. Without that column a change in the
*input image* reads as a difference between the *libraries* — which is
exactly how a 3× speedup appears from nowhere.

**3. Report adjacency with every content row.** `adj%` is the share of
pixels byte-identical to the previous one, i.e. precisely what a
one-pixel cache can hit. Both harnesses compute and print it. It is the
single number that explains every difference between content rows.

**4. The noise generator has bitten us twice — check any new one for
BOTH properties.**

- Use `Math.imul`, not `*`. The C generator wraps in uint32; the naive JS
  transcription `seed * 1103515245` runs in f64, blows past 2^53, loses
  the low bits and collapses into short cycles. Measured adjacency:
  **21.6 %** — the row meant to give lcms's cache *nothing* was handing
  it a fifth of the pixels.
- Take the **high** bits, not the low. An LCG's low bits have period 256,
  so `seed & 0xff` produces a buffer of only **256 distinct colours**
  while still reporting 0.0 % adjacency. The defect is therefore
  invisible in the metric the harness prints. `seed >>> 23` gives
  ~1,016,892 distinct colours per megapixel at the same 0.0 % adjacency.

Adjacency alone does not detect the second one. That is what the
coverage rule is for.

**5. Report CLUT coverage, and size the buffer against the grid.**
`cover` is distinct input colours ÷ CLUT cells. Below 1× the input
carries fewer colours than the table has cells, so most of the table is
never read, it stays resident in L1, and the measurement describes a
working set no real image produces.

| workflow | grid | cells | 1 M px gives |
|---|---|---:|---:|
| RGB-source (3D) | 33³ | 35,937 | ~28× |
| CMYK-source (4D) | 17⁴ | 83,521 | ~12× |

Those are the common shapes for RGB and CMYK profiles, not an artifact
of GRACoL. Note that **64 K px under-samples a 4D CLUT** (~0.8×), which
is why 1 M px is the size the published content table uses.

**But coverage alone is not enough — ordering costs more.** `cover`
counts which cells are touched, not the order. A rainbow sweep or smooth
ramp walks the cube predictably, so the prefetcher keeps up and the hot
window stays tiny however many cells it eventually visits. The `sweep`
generator demonstrates it: same ~1 M distinct colours and same 0.0 %
adjacency as `noise`, **2.1× faster** (190.3 vs 89.0 MPx/s, RGB→Lab).
`sweep` is even faster than the old degenerate 105-colour generator — so
a rainbow ramp is a *weaker* test than the bug we removed, while looking
more rigorous. Never make a smooth synthetic ramp the headline row.

**6. One process per cell.** Running several rows in one process gave
59.5 MPx/s where an isolated run of the identical workflow, content and
size gave **75.4** — a 27 % swing caused only by which rows had already
gone through that call site. V8 specialises a call site to what it has
seen; five different buffers means it specialises for none, and warmup
inside that process does not undo it. `--isolate` spawns a fresh process
per cell so each gets its own heap and its own warmup. It is slower, and
it is the only mode whose rows can be compared.

## Content generators

| name | what it is | adjacency |
|---|---|---|
| `noise` | per-byte PRNG (high bits), every pixel unique, ~1M distinct colours | 0.0 % |
| `gradient` | smooth ramps quantised to 4–8 px flat runs | ~75 % |
| `blocks16` | Marti Maria's generator: 16×16 flat colour blocks | 93.8 % |
| `solid` | one colour everywhere — the cache ceiling | 100 % |
| `photo` | the decoded corpus, tiled | ~17 % (corpus mean) |
| `sweep` | ordered walk of the colour cube — same coverage as `noise`, opposite locality | 0.0 % |
| `noisy:<base>:<n>` | any base blended n % toward `noise` — base ∈ photo·gradient·solid·blocks16·sweep, deterministic, endpoints exact | varies |

The synthetic four bracket the cache — nothing at one end, everything at
the other — but no real image sits at either. That is what the photo row
is for.

## Workflows

`RGB→RGB (matrix)`, `RGB→Lab`, `RGB→CMYK`, `CMYK→RGB`, `CMYK→CMYK`,
`RGB→RGB (softproof)`.

RGB→RGB is sRGB→AdobeRGB1998, never sRGB→sRGB: both engines detect the
identity and collapse it, which measures nothing. Soft-proof
(sRGB→GRACoL→sRGB) is the other RGB-in/RGB-out workflow and it *does* go
through a 3D LUT, so the pair separates "matrix-shaper fast path" from
"interpolation" at identical pixel formats.

## Reading a result

- **jsCE is content-neutral but not locality-neutral.** Its kernels hold
  no memo, so throughput does not track *adjacency* — but it does track
  how much of the CLUT the input touches. Measured on one workflow at a
  fixed 1 M px and a fixed 41,077-colour multiset, purely by reordering
  the same pixels:

  | arrangement | jsCE SIMD |
  |---|---:|
  | photo, sorted by colour (maximum locality) | 175.6 |
  | photo, natural order | 111.9 |
  | photo, shuffled (no locality) | 96.2 |

  So read the jsCE columns against `cover` and against spatial
  coherence, not against `adj%`. Reversing the measurement order
  confirmed this follows the content, not thermal drift or position in
  the run.
- **The pixel-cache table is separate on purpose.** `pixelCache` is a
  beta feature on the *accuracy* path (`buildLut: false`), which is an
  order of magnitude slower than the LUT kernels. It is reported against
  its own uncached baseline; putting it in the main table would invite
  a ratio between two different things.

## Known asymmetry

The JS figures run on Node under Windows; the native figures run under
WSL2 Ubuntu on the same physical CPU. WSL2 is a virtual machine, so a
few per cent of the native/JS gap could be the environment rather than
the engines. It is stated rather than corrected for — the alternative is
a native Windows lcms build, which introduces a different compiler
instead of removing a variable.

## Reproducing the old, defective numbers

`--legacy-noise` reinstates the pre-2026-08 generator verbatim — f64
overflow and low-bit extraction — so historical figures can be
regenerated, and so "did the defect favour one engine?" can be answered
by measurement instead of assumption:

```bash
node run.js --isolate --sizes 1048576 --content noise --legacy-noise
```

Run against the normal output it forms a clean A/B: same harness, same
isolation, only the content differs. The answer it gave is that the
defect was **shared but not neutral** — jsCE's SIMD tier lost 39–54 % on
a correct input where `lcms-wasm` lost 3–26 %, so the old *ratios* were
overstated by 24–52 %, not just the MPx/s. Detail:
[deepdive/benchmark.md § 20](../../docs/deepdive/benchmark.md#the-defect-was-shared-but-it-was-not-neutral).

Keep the flag. The next time a harness change moves the numbers, this is
how you find out whether it moved them evenly.

## Sweeping locality instead of quoting a point

`noisy:<base>:<n>` blends any base content toward the noise buffer, so
locality can be swept as a curve rather than sampled at one arbitrary
content:

```bash
node run.js --isolate --sizes 1048576 --workflows Lab \
  --content "noisy:solid:0,noisy:solid:1,noisy:solid:2,noisy:solid:5,noisy:solid:10,noisy:solid:100"

node plot_noise_bases.cjs ../../docs/deepdive/images/noise-locality-bases.svg "RGB -> Lab" \
  photo=curve_photo.txt gradient=curve_gradient.txt solid=curve_solid.txt
```

`--workflows` takes a substring (`Lab`, `CMYK -> CMYK`), because a sweep
of ten points should not pay for six workflows it is not asking about.

**What it showed.** Three bases starting at 182 / 183 / 119 MPx/s
converge to within a few per cent once 2 % noise is added — so most of
the apparent difference between content types is unrealistically clean
input rather than anything about the engines. lcms drops off a cliff
(92.0 → 33.7 at 1 % noise) as its memo cache stops hitting; jsCE drops
for a different reason entirely. Detail and the benchmark-design rules
that follow from it:
[deepdive/benchmark.md](../../docs/deepdive/benchmark.md#every-starting-content-converges-on-the-same-answer).
