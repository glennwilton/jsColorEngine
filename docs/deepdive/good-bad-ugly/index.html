Filter pipeline with pluggable strategies. Many filters share one dispatch site. The IC at this.current.run(input, output) has seen many distinct callees and is forced megamorphic.

Schrödinger's Bench bites back

This page is a failed experiment, and that is the lesson. We deliberately built three call shapes — a polluted strategy IC, a tidy wrapper, and a bare isolated module — expecting roughly the 100 / 175 / 200 MPx/s split that the registered framework in samples/benchmark/ actually shows. The standalone page refuses to play along. V8 inlines everything anyway.

Why? The original 100 MPx/s collapse needs a very specific recipe: a shared benchmark harness that registers N different transform functions and dispatches them through one bytecode location across repeated benchSingle() invocations, until that IC accumulates enough distinct callees to go megamorphic. Hand-rolling that pattern in a single, focused page is hard. There are too few neighbouring functions for compilation-unit interference, and modern V8 speculatively re-monomorphizes call sites that go quiet.

So the practical takeaway flips: your production code is probably fine. A polymorphic wrapper, a route registry, a plugin pipeline — all routinely run at full kernel throughput because V8 can see the hot callee. The numbers in benchmark.md still stand: 104 vs 175 vs 203 MPx/s is real, measured, and reproducible inside the actual framework. But it is mostly an observing-machinery problem, not a production-code problem.

If you can't reproduce Schrödinger's Bench in a small demo, that is the result. The bench harness in samples/benchmark/ is one of the few real-world places where the call site stays megamorphic long enough to actually hurt.

The accidental headline

Here is the irony, and it is the nicest accident of this page: the experiment failed precisely because all three call shapes — a polluted plugin pipeline, a tidy class wrapper, and a bare-bones isolated module — clear 200+ MPx/s on the same hardware. Three different abstractions, all hitting the kernel ceiling. The page set out to make jsColorEngine look slow under abstraction and ended up demonstrating the opposite: the engine is fast enough that the wrapper shape barely matters. The 100 MPx/s framework number is a measurement artifact; the 200 MPx/s number is what your code can actually see.

When you should still worry

A large, long-lived app can drift into the pathology if all three of these are true at once:

  • One shared dispatch point — a pipeline.run(), effect.apply(), or strategy.execute() call that every operation flows through.
  • Genuinely diverse callees behind it — many different Transform instances, plug-ins, or filter classes whose run() bodies have different shapes.
  • A tight outer loop where dispatch overhead matters — per-pixel transforms, per-frame video, per-tile batch processing.

Examples worth profiling: photo editors with 30+ effects sharing one apply() path, server pipelines that cycle through many ICC recipes through a generic dispatcher, frame-by-frame video filters registered with a central engine. If a profile shows time inside the dispatch wrapper rather than the kernel, this is the smell.

The mitigation is the same as the bench framework's: keep the hot path monomorphic per route. Bind one Transform per route object, give each route its own narrow loop, or use Transform.compile() to generate a fresh function for that route. See benchmark.md §19 for the full escape-hatch hierarchy.
